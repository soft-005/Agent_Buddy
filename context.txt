Building this means stitching together four separate systems — there's no single framework that does all of it. Here's the breakdown:

**1. Always-on-screen overlay**
- Desktop: Electron or Tauri with a transparent, always-on-top, click-through window. This is how most "desktop companion" apps (like virtual pet apps or VTuber overlays) work.
- Mobile: much harder — iOS/Android don't allow persistent floating overlays without special permissions (Android's `SYSTEM_ALERT_WINDOW`; iOS basically blocks this outside widgets/Live Activities).

**2. 3D avatar + customization**
- Rendering: Three.js or Babylon.js (web/Electron) or Unity (native, more polish, bigger footprint).
- Rigging: VRM format (from VTuber tooling) is the easiest path — it gives you a standard humanoid rig, blendshapes for lip-sync/expressions, and a huge ecosystem of free/customizable models and editors (VRoid Studio for building custom avatars without modeling from scratch).
- Animation: drive mouth movement from TTS audio amplitude/visemes, and expressions from sentiment of the agent's response.

**3. The actual agent**
- An LLM backend (Claude API, or others) handling conversation + memory.
- STT (speech-to-text) for voice input, TTS for voice output — this is what makes it feel like "Pi" rather than a chat window.
- A lightweight local client that streams audio/text to your backend and renders the avatar's reactions.

**4. Cross-device sync**
- Conversation state and memory should live server-side (a database keyed to a user account), not on-device — this is what makes sync trivial rather than a P2P nightmare.
- Real-time sync between open clients: WebSockets or a service like Supabase/Firebase realtime, or Ably/Pusher.
- "Same network" isn't actually necessary or advisable — device discovery over local networks is fragile (NAT, firewalls, different subnets). Centralizing through your own backend is simpler and works anywhere the devices have internet.

**Realistic build order**: get the LLM agent talking over text first → add TTS/STT → add the VRM avatar reacting to it → wrap in Electron for the always-on-top overlay → add multi-device sync last, once the core loop works on one device.

Got it — that's the avatar/agent companion project. For the STT piece specifically, running it on an 8GB VPS is very doable, but the right choice depends on whether the VPS has a GPU or is CPU-only (most cheap VPS providers are CPU-only).

Best option for a CPU-only 8GB VPS: faster-whisper or whisper.cpp

Both are optimized reimplementations of OpenAI's Whisper that run well on CPU without needing a GPU.
Model size tradeoff on 8GB RAM:
small (~1GB) — good balance, real-time-ish on decent CPU, solid accuracy
base (~500MB) — faster, noticeably less accurate, fine for short commands
medium (~3GB) — better accuracy but will be slow on CPU-only, and eats a big chunk of your 8GB alongside everything else running (your agent backend, LLM API calls, WebSocket server, etc.)
For a conversational companion where responsiveness matters, small is usually the sweet spot on CPU.

Architecture-wise, for your setup:

Client (Electron/mobile) captures mic audio, streams it to your VPS over WebSocket
VPS runs faster-whisper (small model) as a lightweight transcription service — just a Python process exposing a WebSocket/HTTP endpoint
Transcribed text goes to your LLM agent backend
Response text goes to your TTS step, audio streams back to the client

When to "outsource" instead of self-host: if you want lower latency and don't mind an ongoing cost, cloud STT APIs (Deepgram, AssemblyAI, or even Whisper via a hosted API) are faster and offload compute from your VPS entirely — worth considering if your 8GB VPS is also juggling the LLM orchestration, WebSocket connections, and TTS. Running everything on one small VPS at once is the real risk, not any single piece.

Good news — same router changes things a lot in your favor. Local network sync is much simpler than what I described for the general cross-device case, since you don't need to worry about NAT traversal, firewalls across networks, or a cloud backend for discovery.

Simplest setup for your case:

Run the backend (LLM orchestration + STT service) on one machine and have the other connect to it over the LAN. Two options for where "the backend" lives:

Option A: Backend on your PC, VPS unused for this

Your PC almost certainly has more RAM/CPU than an 8GB VPS, so this is actually the better home for STT + agent logic if you're not leaving the house.
PC runs the WebSocket server + faster-whisper.
Mobile connects to your PC's local IP (e.g., 192.168.1.42:8000) over WiFi.
Downside: only works when you're on the same network — no access away from home unless you also expose it externally later.

Option B: Backend stays on the VPS

Both PC and mobile connect to the VPS over the internet, same as before — being on the same router doesn't change anything here, they just both route out to the VPS.
Upside: works from anywhere, not just at home.
Slight latency cost vs. local, but with a small model like faster-whisper small, this is usually negligible.

For device discovery/connection on LAN (if going with Option A):

Simplest: just hardcode your PC's local IP in the mobile app's config, or set a DHCP reservation on your router so the PC's IP never changes.
Slightly more robust: use mDNS/Bonjour (e.g., mypc.local) so you don't have to hardcode an IP — most routers/OSes support this out of the box, no extra service needed.
Skip anything heavier (Ably/Pusher/cloud realtime) — that's solving a problem you don't have at this scale.

My actual recommendation: since it's just you, and both devices are usually on the same router — go with Option A (backend on PC). It's simpler, free, faster, and you already have the horsepower sitting there. Save the VPS for if/when you want access away from home.

Set WHISPER_MODEL=base for quicker transcription, with slightly lower accuracy.

Personality: edit SYSTEM_PROMPT in config.py to change Buddy's name, character and style.
Creativity: change temperature in providers.json. Lower values give steadier answers, higher values more creative ones.
